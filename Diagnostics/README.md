A controller has a local, irreversible session revocation flag. A revocation request blocks new requests through that session and tries to stop without waiting; a busy recorder or in-flight presentation returns pending and requires an explicit retry. Completion applies to that controller and its shared views: the recorder is stopped and their presentation gate is idle, so those views will not initiate another old-result presentation. A capture or setter already in progress may complete before confirmation. A real unload event, callback ordering, UI thread and automatic retry are not established. A new city or independent session requires a new recorder and controller; a caller that never requests revocation cannot be protected by it. Session ownership prevents ordinary cross-controller misuse but is not a security boundary against arbitrary code in the same process.

The first controller to bind at construction owns its recorder for that recorder lifetime; another controller cannot take it over, including before the owner starts or after it stops or revokes. Binding is non-blocking, and an unsuccessful controller is not an operational owner. If an unbound controller reports successful revocation while the recorder is idle, that does not prevent the actual owner from starting later. The internal `Record*` methods require the adapter to already hold the recorder gate; arbitrary same-assembly calls that violate this contract may interfere. After revocation the view does not display a pending status or offer a working Stop retry: a future host must retain and explicitly retry `RevokeFromHost`, interpret its return and handle its own status. No automatic clearing of previously displayed text is provided.

Revocation cannot retract a snapshot or string already handed to a caller, text already assigned to a field, host or extension copies, event propagation, undo data or logs. The UI host may retain or relay the relative values. A managed thread ID comparison neither authenticates the thread nor proves Unity UI affinity. ## Data and bounds

If a future caller supplied already-existing manager references and a separately reviewed opt-in were implemented, the adapter's allowed game reads would be loading flags, simulation frame, per-frame duration, day/night phase, reference frame/timer and displayed day/night hour. It does not call `Singleton<T>.instance`, read an absolute date, metadata date, account or city name, open a save, initiate a save, write a game field, or use file or network APIs. The caller's own method of obtaining references is outside this candidate and is not proven side-effect-free.

Each independent stream holds at most eight records. Frame and display records contain signed endpoint differences and uncertainty markers, not absolute calendar dates or save paths. Raw frame and phase values are held transiently as in-memory baselines for the next difference; those values and the resulting differences are still game state and are not guaranteed to be anonymous. No automatic output or persistence is provided.

The diagnostic uses a private non-blocking gate and rejects a competing attempt. A contention marker may be set after the current holder has already committed a record, so an accepted record does not prove that callbacks did not overlap. Every record explicitly keeps `ConcurrentCallbacksExcluded`, `LifecycleContinuityVerified` and `CityIdentityVerified` false. The caller-supplied generation and loading-flag endpoints cannot authenticate a city or rule out an ABA transition. Every phase record retains `PhaseMayWrapOrJump=true`; its signed difference is an endpoint comparison, not confirmed phase progress.

`ElapsedCounterTicks` is the difference between raw `Stopwatch` counter values. A record does not retain `Stopwatch.Frequency`, so the difference is not directly a duration in seconds or in 100-nanosecond `TimeSpan` ticks. The test-only stop method returns false when busy; it does not schedule a later stop. Only a successful return confirms that test instance has stopped.
