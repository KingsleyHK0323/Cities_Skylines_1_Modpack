# Lifecycle observation review plan

Status: review proposal. No game, Steam, installation, save, native unlock or game UI was used. The existing `Diagnostics/LifecycleCaptureCandidate.cs` remains the only proposed lifecycle-capture implementation; do not duplicate it. Its reference-built candidate is disabled, has no real activation, stop, readout or display entry, and is excluded from the main Release source list. Its public mod and loading-interface types could be discovered if installed, but actual discovery has not been tested.

## Scope and privacy

The intended observation is a bounded, memory-only trace of loading callbacks. Each entry contains only relative `Sequence`, fixed `EventCode`, locally allocated `Instance`, locally allocated `Generation`, and reduced `Mode`. Codes 1–4 denote created, loaded, unloading and released callbacks; mode is 0 when inapplicable, or 1–4 for ordinary new game, loaded game, scenario and other. No city or save name, player or account identifier, file path, balance, coordinate, tile state or area count is part of the trace. The current buffer permits at most 64 entries and 32 instance and generation labels. Local labels and event order can still identify or encode information; they are not anonymous or authenticated.

An entry's interval is the diagnostic interval in which the record is accepted under the buffer lock. It does not establish when the game originated the callback, which city it belongs to, or uninterrupted loading ownership. The synthetic tests show that an earlier test delegate delivered after stop and restart is accepted in the later interval; this is not a real game callback or a reproduction of an already-entered callback waiting on the lock. Do not infer missing earlier callbacks, a current city or permission to write.

`Manual activation` means a visible, explicit start action in the future diagnostic interface, with collection off by default. It is not a guarantee that a human physically initiated the event. Other fully trusted in-process code may call public UI methods, simulate a click, use reflection or inspect memory. This candidate must not itself write files or settings, use the clipboard, access the network, or modify game state; that restriction cannot guarantee what the game, UI templates, listeners, patches or other extensions do.

## Observed UI and trust limits

- In the inspected reference, `OptionsMainPanel` finds `OnSettingsUI` by reflection. Opening or rebuilding the settings panel can call it, so registration must not activate collection.
- `UIHelperBase.AddButton` takes a text label and parameterless callback; the API supplies no authenticated user-input provenance. `UIComponent.SimulateClick` is public and can route through `OnClick` to the registered click event. A visible button is an explicit interface action, but the callback alone cannot distinguish a physical click from another extension's invocation.
- `UIHelperBase` has no general label/update method. The inspected `AddGroup` implementation uses a `UILabel` for the group title. Its text-change path notifies listeners and invokes receivers on the label's own GameObject; it does not by itself establish propagation to the parent. Click events may also be delivered to other listeners or parent components. Do not send sensitive text, raw exceptions or arbitrary strings to these interfaces.
- Plugin or locale changes can rebuild and destroy settings controls; old closures and control references cannot be presumed live. The inspected plugin-change path may rebuild on the caller's thread, so `OnSettingsUI` does not independently prove a Unity UI thread. `Dispatcher.currentSafe` and `mainSafe` are non-creating static-field reads in the inspected copy, but their equality is only a hint: `Dispatcher.current` has a public setter and the main dispatcher is established by construction. `ThreadHelper.dispatcher` can call an initializer that creates Unity objects.
- The inspected game UI exception path can call game logging or forwarding methods. The diagnostic can avoid making its own file, clipboard or network calls and avoid putting sensitive values in exceptions, but cannot promise that the whole game process never logs or emits data.

These observations come from the authorized copies of `ICities.dll` (SHA-256 `466586ADB50DCC2E1382D9F7683FA50FEBA82A376D736FB65F1C34A53D0B9C90`), `Assembly-CSharp.dll` (`DF557994A03C93D8BB4A14F80B1FBCC0FB29D547658442445D078D069BCDD9FE`) and `ColossalManaged.dll` (`34701F61DEF31F5F9DF79D573CE19E0BC52575879BCC395D51B39F6D746A58B9`). They are static findings about those copies, not live-game validation.

## Future implementation and review conditions

1. Reuse the existing buffer and separate diagnostic build. Add visible start, stop, status and view actions only after a reviewed UI-thread boundary exists. Creating, rebuilding or rendering the panel must not enable collection. Release source and artifact checks must continue to exclude the candidate and its test controls.
2. Give each registered UI page an opaque, non-reused registration token. A closure must check the current token and readiness in the same synchronization boundary as its internal state transition; callbacks during registration and callbacks from a closed or replaced page must not start a new collection. Closing or attempting to replace a page should stop its active capture and invalidate its closures, including when the replacement fails, so the user does not lose control while collection continues. Do not hold the page lock across calls to an external UI helper that could wait for another thread to reenter. The synthetic same-thread reentrancy case does not prove cross-thread helper safety. This fence protects that UI registration only; it does not authenticate game callbacks, cities, threads or the physical source of a click.
3. Prefer one bounded collection interval per process until an explicit retention and reset policy has been reviewed. Stop must prevent new entries; retained data and any later view must be visible to the user. Show overflow and missing data as incomplete. The current synthetic restart retains old records and can admit a delayed work item into the later interval, so it is not a verified session-isolation design.
4. Construct any displayed text solely from fixed labels and the five integer fields; bound both record count and presentation length. Do not add file, clipboard, network, preference, game-write or raw exception output. Verify the actual UI implementation, listener exposure and destroyed-object handling before game use.
5. Keep diagnostic data observational. Fabricated or delayed callbacks, local labels, a current UI-page token and claimed snapshots must never authorize a native submission. In the main project's source list and the combined synthetic fixture, `StartupSnapshots.PrepareNativeSubmission` and `DisabledNativeStartupSubmission.Submit` each return `Unavailable`. The hosted `game-dll.yml` direct source list includes the former via `GameObservation.cs` but omits `NativeSubmissionCandidate.cs` and therefore does not compile the latter. This describes the current source lists, not a verified hosted artifact; an independent third-party implementation is outside the guarantee.

The test-only page-gate fixture checks registration reentrancy, failed replacement and replaced-page callbacks without connecting an actual UI. A separate active-page case checks that close stops subsequent records and prevents its old click from restarting capture. These sequential cases do not establish real UI concurrency. Their limitations and the forged/delayed submission checks are recorded in `Local_Validation_20261113_FullMap/EVIDENCE.md`; these are fake-boundary checks, not game or UI acceptance.

## Proposed observation after separate approval

After the missing UI conditions and a diagnostic binary have been reviewed, separately authorize the exact game launch, mod arrangement and disposable test environment. First confirm default-off behavior, then start a single bounded trace by the visible action and inspect only allowlisted in-memory codes for creation, ordinary new-game loading, unload and release. A callback before activation, an absent callback, a replaced UI page, truncation or any uncertain origin remains unknown rather than a pass. Stop if unexpected data, an unexpected write, a UI exception or conflicting ownership is observed. Do not copy or upload the event sequence without a separate decision.

This lifecycle-only pass cannot authenticate snapshot provenance, simulation-thread identity, forced-pause state, all 25 tiles, no debit, native side effects or save compatibility. Those remain separate prerequisites described in [25-area release evidence](25_Area_Release_Evidence.md); real game writes require separate design and explicit authorization.
