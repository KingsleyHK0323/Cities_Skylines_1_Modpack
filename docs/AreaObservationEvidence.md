### Lifecycle and snapshot research

The inspected `LoadingManager.<LoadLevelComplete>c__Iterator9.MoveNext` sets `m_loadingComplete` true before it invokes `LoadingWrapper.OnLevelLoaded`; the wrapper forwards the mode to each `ILoadingExtension.OnLevelLoaded`. `LoadingExtensionBase.OnCreated` stores its `ILoading` reference, whose `loadingComplete` property reads that volatile flag. `ILoading.currentMode` returns `AppMode`, not `LoadMode`: `Game` does not distinguish a new game, a loaded game, or a scenario. The reference getter also has a default path returning the `Game` enum value for unmatched availability values, so that property alone is not sufficient to classify a startup.

The inspected `ICities.IThreading.QueueSimulationThread(Action)` returns void. Its `ThreadingWrapper` invokes the action directly if already on the simulation thread; otherwise it calls `SimulationManager.AddAction`. Queueing alone neither establishes that the action will run nor that its original city is still current. `ICities.IThreading` does not expose an independent current-thread identity check. The inspected wrapper compares `Thread.CurrentThread` with `SimulationManager.m_simulationThread`, a public field in this assembly copy; using that field would require a verified manager identity, compatible game assembly and patch assumptions. The inspected `ColossalFramework.Singleton<T>.instance` getter may create a Unity object and component when no instance exists; it cannot be assumed to be a side-effect-free lookup. The adapter does not perform that comparison or access that singleton and marks `SimulationThreadVerified` false. A fake scheduler calling on the wrong thread can produce only an unverified observation, never a native submission.

The read-only adapter captures `IThreading` and schedules an observation action; it rechecks its recorded lifecycle and readiness inside that action and has no write path. A queued call can still reach an old scheduler if invalidation races with submission. Invalidation can also occur after a ticket check and before an external getter begins or finishes, so a stale getter call cannot be ruled out; publication rechecks the ticket under the state lock. Actual scheduler behavior and thread identity remain unverified.

The adapter retains the actual `LoadMode` from `OnLevelLoaded` against its recorded loading owner and a fresh local generation; only ordinary `NewGame` schedules a snapshot. `LoadGame` and `NewGameFromScenario` do not auto-unlock under the current conservative assumption. Scenario support remains an open product decision. The action rechecks recorded owner, generation, provider, `loadingComplete`, app mode and the exposed pause flag before individual grid reads. When that flag reports pause, `WaitingForResume` permits an explicit observation request; the new action revalidates its lifecycle and readiness, and no write is retried. A pause can still begin and end between checks, or race a getter already starting. In the inspected assembly, `IThreading.simulationPaused` reads only `m_simulationPaused`, while `FinalSimulationSpeed` also checks `m_forcedSimulationPause`. Therefore a false exposed flag does not establish that the simulation is running; snapshots mark `SimulationRunningVerified` false. The reference instruction order is not proof that all area data is ready, that cross-thread operations are atomic, or that callbacks always originate from the current city. In particular, a delayed unload from an earlier city on a reused loading instance is indistinguishable from the current city's unload.

### Candidate milestone strategy and side effects

The inspected `CanUnlock` returns false for an invalid coordinate, maximum count or area milestone before it calls `OnCanUnlockArea`; overriding that later callback cannot bypass those earlier gates. In this assembly copy, static call-site search found `UnlockManager.Unlocked(Int32)` in both `GameAreaManager.CanUnlock` and `GameAreaManager.SimulationStepImpl`. A global override could therefore also affect the latter's area guide. `UnlockAllProgressionMilestones` iterates progression milestones and checks other milestones, so it is not an area-only bypass.

An independent static IL review of the same reference found that `CanUnlock` computes adjacency at IL_005B–0095 and passes the Boolean to `AreasWrapper.OnCanUnlockArea` at IL_0096–00A6; the wrapper replaces that Boolean with each extension's return at IL_0007–001D. After the earlier coordinate, maximum, milestone and ownership checks pass, an extension can therefore change a nonadjacent `false` to `true`; adjacency must be independently enforced if it is the adapter's policy. The `FakeEligibility` fixture in `Tests/PreviewChecks.cs` rejects nonadjacent input before its extension result, so that fake is stricter and cannot prove the native extension chain preserves adjacency.

The same review found that `AreasWrapper.CanUnlockArea` calls native `CanUnlock` at IL_0000–000D; a later native `UnlockArea` calls `CanUnlock` again at IL_0011–0014. A separate preflight can therefore repeat extension callbacks. The public `AreasWrapper.maxAreaCount` getter reads the raw backing field at IL_0000–000B, whereas native `GameAreaManager.get_MaxAreaCount` writes the default value nine when that field is zero at IL_0000–0019. Consequently a zero raw value is not necessarily the effective native maximum, and the eligibility preflight itself may initialize game state. These are reference-IL conditions, not observed game behavior; do not treat such a call as proven side-effect-free.

#### Area-specific gate inventory and implementation limits

The authorized `ICities.IAreas` interface has an area-maximum setter but no area-milestone setter. `AreasWrapper.set_maxAreaCount` clamps to 1–25 and writes the backing maximum; when the value changes after loading completes it invokes or dispatches `UnlockManager.MilestonesUpdated`. The inspected event subscribers include `BuildingManager.RefreshUnlocks` and several panels. The building refresh can conditionally mark already-eligible buildings unlocked and call an achievement; this does not mean every maximum change unlocks buildings or that the setter directly changes milestone progress. Terrain patch handling can reallocate larger arrays based on the maximum. The inspected area serializer stores count, starting tile and grid, not the maximum in that method; deserialization raises the maximum to at least the restored count. Actual memory, event, save and cross-city behavior remains untested.

`UnlockManager.Unlocked(int)` reads the public `UnlockController.m_AreaMilestones` array through its properties. In the inspected IL, missing properties cause a call to `Unlocked(null)`, which returns true; a null or empty array with non-null properties is not a usable index and can throw. For a nonempty array, the requested count is clamped to its actual bounds. A null entry returns true; a non-null entry with null milestone data returns false, and a nonzero passed count returns true. The runtime array length and configured milestones are not known from this reference. For example, counts at or above nine all map to index eight only if the array length is exactly nine.

Temporarily nulling one element is grounded in this reference's area-gate logic and does not itself mark the original milestone passed. It is not confined to the targeted `CanUnlock` call: direct reads of the same field also appear in `UnlockManager.SimulationStepImpl`, `CheckAllMilestones`, `ResetWrittenStatus`, `ResetMilestones`, `UnlockingPanel.RefreshMilestonesPanel`, `UnlockManager.Data.Serialize` and `AfterDeserialize`. A null entry can be skipped by milestone checking or post-deserialization; the inspected serialization helper passes a null element to its serializer, but the resulting bytes and save consequences were not inspected. `GameAreaManager.SimulationStepImpl` also calls `Unlocked(count)` for an area guide. Whether any of these readers actually interleave with an experiment is not known.

In the inspected ordinary save path, `LoadingManager.SaveLevelCoroutine` queues `SaveSimulationData` on `SimulationManager`; the latter calls `DataSerializer.Serialize` and collects manager data. This does not prove every serializer invocation is confined to the same thread or excludes synchronous reentry: `UnlockManager.Data` and `DataSerializer.Serialize` are public, and area extensions are invoked synchronously on the native unlock stack. An extension could theoretically serialize a container during its callback, but no extension doing so or resulting save effect was observed.

`UnlockController` has multiple public `MilestoneInfo[]` fields for progression, features, areas, zones, services and policies; runtime array aliasing is not established. Cloning the area array before nulling one entry avoids changing the old shared array's element, but publishing that clone in `m_AreaMilestones` still exposes the temporary value to all area-field readers. Two overlapping clone-and-restore scopes can restore an older temporary clone instead of the original; reference comparison or a compare-and-swap cannot detect every ABA or earlier reader. `finally` does not undo a serialized null, an observed guide or callback effect, or a partial native unlock. This is a concrete experimental idea, not an implemented or accepted safe boundary.
