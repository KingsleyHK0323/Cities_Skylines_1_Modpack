# Read-Only Game Validation Plan

Status: proposed for Main review. No game, Steam, real save, installation, diagnostic export, or publication was performed or authorized by this plan. The current module has no native area submission and its submission candidate is disabled.

## Scope and prerequisites

Before any future game operation, obtain explicit authorization for the exact game installation, mod deployment method, temporary test-city or test-save location, diagnostic build, observation steps, and evidence directory. Preserve existing saves, mods, settings and logs. Do not infer these locations from examples or inspect a player's existing save. Use an isolated, disposable test city and, if load-game coverage is authorized, a separate disposable test save chosen by the user. Scenario testing remains optional and requires a separate disposable scenario. Do not start Steam or the game, install a mod, create a save or change settings under this plan alone.

Verify the proposed DLL and authorized reference copies by hash, the intended game and ICities versions, the selected build and its enabled features. Record only the approved version labels and hashes; do not record the installation path, Steam account, machine identifier or user profile. A matching binary and successful compilation do not establish game behavior or callback ordering. Other mods and the game itself may read or write files, emit logs, or perform other side effects; this module cannot promise a side-effect-free game process.

## Two privacy levels for optional instrumented observations

These are optional instrumentation choices, not prerequisites for a player to observe the existing game screen. See the [minimal integration design](25_Area_Minimal_Integration_Design.md) for the current shortest-path proposal and its unresolved native-write blockers.

1. **Lifecycle-only option.** Prepare and separately review a game-connected diagnostic build that does not call `IAreas.unlockedAreaCount` or `IAreas.IsAreaUnlocked`, does not schedule the current startup grid snapshot, and emits only reviewed lifecycle and scheduler outcomes after explicit activation. The earlier `Diagnostics/LifecycleTraceCandidate.cs` data library has no game extension, callback wiring, user-visible activation, file output, or network output. The newer `Diagnostics/LifecycleCaptureCandidate.cs` has been directly compiled against local game references and declares game loading interfaces, but is disabled and has no actual activation, readout, file, clipboard or network path. If installed it could be discovered and receive callbacks, but the reference-built candidate discards them. It is not ready for game use. The separately compiled `RedactedDiagnosticBuffer` is also default-disabled, not wired to game callbacks, and has no file exporter.
2. **Disposable new-city observation.** Only with separate explicit authorization, evaluate the current read-only snapshot adapter in a disposable ordinary new city. It reads each of 25 unlocked flags twice and the unlocked count into memory; that is city-state collection even when no grid is written to a log. Keep individual coordinates, tile flags and counts out of retained evidence. Other game modes must not trigger the snapshot. Reporting this adapter's internal results requires a separately reviewed evidence channel; player observation of the existing game screen needs no such channel and does not itself authenticate the snapshot.

The existing DLL is not a lifecycle-only diagnostic build: its ordinary `NewGame` path can queue and retain a read-only grid snapshot. Do not use it to claim zero city-state collection.

## Loading-capture build boundary

`LifecycleCaptureCandidate.cs` is included only with `FULL_MAP_LIFECYCLE_DIAGNOSTIC` and is suppressed if either `RELEASE` or `FULLMAP_RELEASE` is defined. Its separate project requires `Configuration=Diagnostic` and `EnableLifecycleDiagnostics=true`, rejects the synthetic test-control symbol, and rejects a Release configuration. The directly reference-built candidate omits `FULL_MAP_LIFECYCLE_DIAGNOSTIC_TEST`; consequently it has no method that enables, stops for review, snapshots, displays or exports records. Synthetic builds use that extra flag only to exercise capture behavior. Reflection or a changed assembly is outside this boundary.

If a future reviewed activation path is added, the capture record has five read-only integers: `Sequence`, `EventCode`, `Instance`, `Generation`, and `Mode`. Event codes 1–4 denote the observed created, loaded, unloading and released callbacks. Mode 0 is not applicable; 1–4 denote ordinary new game, loaded game, scenario and other. At most 64 records, 32 instance labels and 32 generation labels are stored per buffer; exhaustion stops collection. The current reference build cannot show its overflow state because it has no display path. Labels are allocated locally, and a generation labels an observed loaded callback, not an authenticated city. If collection starts after an instance was created, the first later callback is not fabricated as a creation event. The lock serializes record writes; a callback that began earlier but reaches the lock after a stop and restart may be recorded in the newer interval. Synthetic restart preserves prior records and does not label intervals separately. None of this establishes callback origin, game thread or anonymity.

The directly implemented `ILoadingExtension` ignores its `ILoading` argument rather than deriving from the reference base class that retains that reference. This describes the candidate's own code, not all game or plugin objects. Fixed event and mode choices can encode information, and the candidate is not a sandbox against full-trust reflection or other mods.

No player-facing display has been connected. In the inspected reference, `OnSettingsUI` is a reflection convention rather than an `IUserMod` member; opening or rebuilding a settings panel is not user consent. `UIHelperBase` has buttons and groups but no general text-label or update API. A button is an explicit user-facing action, not proof of a human click: the reference also exposes `UIComponent.SimulateClick`, and another in-process extension may invoke the same callback. The concrete group implementation sets a label; its text-change path notifies registered listeners and receivers on the label's own GameObject. This evidence does not establish automatic upward propagation to the parent. Panel rebuild and object lifetime are also relevant. A plugin-change path can invoke settings reconstruction on the caller's thread, so a trustworthy Unity UI-thread boundary has not been established. A game helper used to dispatch to the main thread may create Unity helper objects and is not proven side-effect-free. A future implementation must establish explicit player controls, safe UI-thread dispatch, bounded presentation, correct panel lifetime and data exposure before it is connected. No clipboard, file or network output is implemented in this candidate; the game and other extensions may have separate side effects.

The main module's normal Release source list excludes the redacted buffer and the public ownership diagnostic getter; the underlying `OwnerAmbiguous` protection and private issue state remain, as do existing observation APIs. The old standalone `LifecycleTraceCandidate.csproj` defaults to a configuration named `Release` and still includes its data-library diagnostic types. It is not the main module project. Neither that old source nor `DiagnosticPrototype.cs` has its own Release preprocessor guard: a different direct compiler command that forcibly includes either file can include its types even with Release symbols. Verify exact source lists, assembly identity and hashes rather than treating a configuration name as proof of exclusion.

The hosted `game-dll.yml` compiler command is another distinct path: it lists only `AreaPreview.cs` and `GameObservation.cs`, does not invoke the main project, and currently defines neither Release marker. Its exclusion of the ownership getter depends on not defining the test-diagnostics symbol; its explicit source list excludes the redacted buffer and both standalone candidates. That list includes `StartupSnapshots.PrepareNativeSubmission` through `GameObservation.cs`, but omits `NativeSubmissionCandidate.cs`, so it does not compile `DisabledNativeStartupSubmission` as the main project does. The command has been updated to include `System.Core.dll`; only isolated direct compilation and static inspection have been performed, not a hosted workflow run. Recheck source lists, flags, metadata and artifact hashes when either build path changes.

The Lifecycle test project deliberately disables implicit configuration symbols and enables its synthetic diagnostic getter; running that test project under a configuration named `Release` is not evidence that the main Release assembly excludes diagnostics. Check the actual main DLL's types and references independently. Also check the actual distribution manifest: inspecting one main assembly cannot prove that a separate old diagnostic DLL was not packaged alongside it. The current workflow configuration names specific output files, but no new artifact or package has been produced or inspected in this work.

## Current standalone schema and proposed storage

The standalone candidate's `ExportUtf8` returns an in-process UTF-8 JSONL byte array without a BOM, with one object per event and exactly these numeric keys: `seq`, `event`, `instance`, `generation`, `queue`, and `mode`. The base event codes are `Created` (1), `Loaded` (2), `ProviderBound` (3), `QueueRequested` (4), `CallbackEntered` (5), `OverlapOrReentry` (6), `CallbackExited` (7), `Unloading` (8), `CallbackAfterUnload` (9), `Released` (10), `LateCallback` (11), and `Truncated` (12). Mode codes are `None` (0), `NewGame` (1), `LoadGame` (2), `Scenario` (3), and `Other` (4). The labels are generated within one trace instance; zero means that the corresponding label is absent. They are session-local pseudonyms, not authenticated city, object, callback, or thread identities. Sequence is recording order under the candidate's lock, not proof of causality or thread identity.

The candidate is disabled by its public constructor and has no public enable method. Its internal boolean constructor is for synthetic tests; same-assembly code or reflection could invoke it, so this is not a security boundary. It stores at most 64 events and creates at most 32 instance and 32 generation labels per trace; exhaustion stops collection and adds a truncation marker to a later export. Filling the final allowed event or label does not itself stop collection; a later attempt beyond a corresponding limit does. At the event limit, Enabled may still be true, but the next otherwise admissible event is rejected, sets overflow and disables the recorder. There is no process-wide bound across multiple traces or copies. `Stop` stops new records but `Read` and `ExportUtf8` can still create new copies of earlier records after stopping; previously supplied copies cannot be revoked. The byte array can be retained or transferred by its caller, although this candidate itself contains no file or network output.

With FULLMAP_LIFECYCLE_SCHEDULER_EXPERIMENT and neither RELEASE nor FULLMAP_RELEASE, the standalone data candidate adds caller-reported QueueReturned and QueueThrew events and per-callback invocation tokens. The caller must report the fake scheduler result and callback entry and exit; the candidate does not invoke or authenticate a scheduler. A saved callback can be reported after an exception or unload. A token can be handed to a different managed thread before exit, so a paired token does not prove one real callback call stack.

ReadObservationDetails returns a separate in-process copy containing Sequence, ThreadTag and Invocation integers for accepted events. Tags are allocated per recorder for the managed thread-local slot that called the recording method, not for an authenticated game or simulation thread. A recorder holds at most 32 marker references; stopping or overflow clears its marker array, but a weak-reference shell may remain in a live thread-local slot. Full-trust code may inspect private markers, and event choices or sequences can be correlated; these are pseudonyms, not an anonymity guarantee. Full-trust reflection can compare a marker shared by active recorders on one managed thread. Read and ReadObservationDetails are separate lock-protected snapshots and can differ while collection continues. Stop prevents further records but does not prove that no callback ran afterward. An overflow truncation entry is synthesized only by the existing JSONL export, not included in either 64-record snapshot.

The existing JSONL object fields are unchanged and do not include ThreadTag or Invocation. Under the experiment its event values may also include 13 and 14, which older consumers limited to 1 through 12 may reject. Same-process callers can retain either snapshot or exported copies; the candidate contains no file or network output, which does not prevent another component from retaining or transmitting data. The new methods and types require the experiment symbol and are suppressed by either explicit release symbol. The main project and inspected hosted compiler source lists omit this standalone source; the old standalone project configuration named Release can still compile the legacy trace types, so a configuration name is not proof that every diagnostic type is absent.

The record has no free-text field, but neither the fixed numeric fields nor the size bound guarantee privacy or anonymity: an untrusted caller could encode information in event choices, mode choices or ordering. A future collector must use reviewed fixed event sources, bound event rates and sequences, inspect actual output, and prevent untrusted callers from supplying arbitrary events. Do not retain free text, raw exceptions or stack traces, absolute paths, timestamps, city or save names, player or account identifiers, coordinates, tile flags, tile counts, money values, screenshots, memory dumps or save bytes. Default-off must be verified after every load; activation, stopping and any later export must be explicit, user-visible and authorized.

The trace is incomplete by design. `Created` does not include the component type, so an instance without later identifying events cannot necessarily be classified. A repeated entry of an already exited queue uses the ordinary `CallbackEntered` code; consumers must compare queue labels to identify that pattern. `OverlapOrReentry` examines depth for a single Threading token and does not identify all cross-token callback overlap or simultaneous Loading instances. Queue tokens do not authenticate which invocation called `Exit`; caller mispairing can misrepresent the observed sequence. Truncation, missing events and untrusted callers make any inferred relationship uncertain. These limitations do not prove a real game callback sequence.

The current requested diagnostic direction is in-memory display only, with no file output. The optional file-storage idea below is outside the present authorization and would require a separate decision and explicit approval before any implementation or use. Proposed evidence directory, to be created only after approval and only if absent:

`<project-root>/Full_Map_Unlock_And_Expansion/Local_Validation_ReadOnly_Game_<unique-local-label>/`

Proposed artifacts are `events.jsonl` (reviewed records only), `summary.md` (pass, fail or unknown for each case, with no raw game data), and `hashes.txt` (hashes of the diagnostic DLL and retained evidence only). No file exporter, game-observation directory or such artifacts have been created. A future file exporter must first establish a safe handle-based destination under the approved root, account for junctions, symbolic links and path replacement races, and use exclusive creation without overwrite; string-prefix checks alone are insufficient. Windows filesystem metadata may still include timestamps. Keep evidence local; do not upload or send it externally without separate authorization. Game-owned logs are outside this module's control and must not be copied into the evidence directory by default.

## Observation matrix

This matrix is a future design, not a list of capabilities already provided by the standalone candidate. In particular, the candidate does not currently report pause, cancellation, `OwnerAmbiguous`, or snapshot results.

| Case | Observe or compare | Expected result and limitation |
| --- | --- | --- |
| Default state | Load the approved diagnostic build without activation. | No module diagnostic records or export; this says nothing about other game or mod logs. |
| Ordinary new game | After authorized activation, record load-mode category, registration, provider binding and queue/callback outcomes. | Only `NewGame` is the provisional snapshot candidate; the recorded local generation is not a native city identity. |
| Disposable load game / scenario / editor | Record only mode category and whether a snapshot was scheduled. | `LoadGame`, `NewGameFromScenario` and editors do not automatically schedule the 25-area snapshot; scenario support remains undecided. |
| Pause and explicit observation retry | Observe the exposed pause flag, waiting state, explicit request and subsequent queue/callback outcome. | No automatic write or write retry; normal pause false does not prove forced pause is absent. |
| Scheduler ordering and unload | Record queued, callback-entered, cancelled and unloaded categories without thread IDs. | Queue return is not completion. Late invalid tickets must not publish; a getter may still race invalidation. Actual simulation-thread identity remains unknown. |
| Provider replacement and overlap | Record provider bind/release and `OwnerAmbiguous` outcomes without identifiers. | Ambiguity stops observation. Missing release may leave it stopped; do not force reset or infer the current owner. |
| Disposable grid observation, only in privacy level 2 | Compute in memory whether coordinates were requested in range, the two reads agree, and count checks pass. Retain only pass/fail/unknown. | Matching reads do not prove atomicity, source identity, causation, no debit, or compatibility with other mods. |
| Recovery and shutdown | Record explicit cancellation, unload and diagnostic deactivation categories. | Future snapshot-ticket goal: an observed invalidation prevents that old ticket from publishing as current. The diagnostic capture does not authenticate callback origin and a delayed item can be recorded in a later interval. Retained references and callbacks not yet observed remain limitations. |

Run synthetic cases first, including stale loading creation, nested same-context eligibility checks, wrong-thread fake callbacks, provider replacement, forced-pause uncertainty, cancelled queues, mixed grids and unknown prior outcomes. A diagnostic-only build must also prove through fake providers that no `IAreas` getter is invoked. These tests are prerequisites, not a substitute for the separately authorized game observation.

## Stop and evidence rules

Stop the future session on an unexpected native write or payment request, unknown or conflicting owner/provider, ambiguous mode or epoch, an invalidated ticket producing a published result, unexpected game or mod interaction, evidence containing non-allowlisted data, an existing output path, a diagnostic exception, or any user request to stop. Do not retry an unknown game write, force owner recovery, change global milestones, install a patch dependency, or clean up automatically. Preserve the observed state and report the exact boundary without copying private values or raw exception text. An absent callback or unavailable evidence is `Unknown`, not success.

Successful lifecycle observation cannot establish safe area submission, no debit, rollback of terrain/zone/achievement effects, compatibility with other patches, save/reload safety, or 81-area behavior. Those require separate decisions, permissions and evidence.

See [25-area release evidence](25_Area_Release_Evidence.md) for the observations and separate write-validation decisions still required before a native adapter can be considered.
