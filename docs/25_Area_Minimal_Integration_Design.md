# Minimal integration design for an ordinary new city's 25 areas

Status: proposal for review, not an implemented or approved game operation. The first-phase goal is all 25 native areas unlocked at startup without debiting city funds. Existing saves, scenarios, editors and 81-area maps are outside that product goal. Current native submission remains disabled. The reference facts below describe the inspected `Assembly-CSharp.dll` with SHA-256 `DF557994A03C93D8BB4A14F80B1FBCC0FB29D547658442445D078D069BCDD9FE`, not an observed game or an assurance about patched versions. See [reference evidence](AreaObservationEvidence.md) and [release evidence](25_Area_Release_Evidence.md).

## Proposed control flow and unresolved prerequisites

1. **Trigger.** `Loading.OnLevelLoaded(LoadMode.NewGame)` is the existing provisional entry point; `ILoading.currentMode == AppMode.Game` alone does not distinguish a new city. Wait for the associated loading, areas and threading providers rather than assuming callback order or area readiness. A duplicate, unsupported mode, unavailable dependency or ambiguous owner must not start a write. The current *snapshot* path is limited to `NewGame`; the module's separate general area observations can also be active in `LoadGame`.
2. **City and provider authority — blocked.** Bind the actual current city, load lifetime and area provider by a relationship that is valid at the write and subsequent observation. Existing local owner references, epochs and tickets only describe received events; an old unregistered instance, a delayed callback on a reused instance, or provider replacement can defeat those assumptions. The available callback arguments do not currently establish an authenticated city identity. A few clean observations cannot prove this boundary. Do not submit until a reviewable mechanism prevents or detects those cases and ties invalidation to the actual native call.
3. **Execution context — blocked.** `QueueSimulationThread` may run inline, enqueue, or never execute, and returns no completion value. The adapter must independently establish that the actual call runs in the correct simulation context, that its city and provider are still current, and that pause state is suitable. The exposed `simulationPaused` flag does not cover the inspected forced-pause field. The inspected manager field is only a possible reference-version research direction; resolving a singleton can create a Unity object and is not an established safe lookup. No adequate context authentication or atomic transition from the last authority check to the native call is established.

   The inspected reference does expose public `SimulationPaused`, `ForcedSimulationPaused`, `SelectedSimulationSpeed` and `FinalSimulationSpeed` getters, as well as `GameAreaManager.GetStartTile`, `IsUnlocked`, `CanUnlock` and `UnlockArea(int)`. The API names are known; the remaining issue is what their values establish at the actual call. In particular, the inspected `FinalSimulationSpeed` getter can access loading and tool managers through singleton lookups that may find or create Unity objects. Reading any of these values at one instant does not prove it remains unchanged for the whole native operation.

4. **Initial observation.** On the verified context, obtain a coherent same-city view of the 25 distinct coordinates, their ownership and count. The current adapter reads each flag twice and the count three times, but matching reads can still be a mixed snapshot; its provenance, real simulation thread and running-state flags remain unverified. A version-appropriate stable boundary and exclusion or detection of concurrent changes are prerequisites, not properties established by the current double read.
5. **One attempt.** Validate raw `x` and `z` independently in `0..4` before flattening; select a locked cardinally adjacent area in a deterministic order. The inspected native method passes its adjacency result to extensions, which can change that Boolean; independent adjacency validation is this adapter's stricter policy, not a guarantee about all extensions. Establish the applicable maximum and milestone without assuming an eligibility call is read-only. `AreasWrapper.CanUnlockArea` invokes native `CanUnlock`, whose maximum getter can initialize a zero backing field to nine and whose extension callback can have other effects. Allow at most one pending native attempt for the authenticated run. A future separately approved design must choose one path: `IAreas.UnlockArea(x, z, false)` once, or the concrete `GameAreaManager.UnlockArea(index)` once. The wrapper returns `void` and may queue; the concrete method synchronously returns `bool` or throws, without a `requireMoney` parameter. Neither is sufficient evidence of a safe or successful transaction. Do not call a second area until the first outcome is resolved.
6. **Confirmation.** Require a later, coherent observation of the same city showing the intended area changed from locked to unlocked, the count increased by one and no unexpected grid change. Establish enough exclusivity or other causal evidence to exclude another actor producing that change; otherwise classify the result as unknown. A normal return, callback, matching local generation or visible balance alone is insufficient. After a confirmed result, repeat the same process for the next adjacent candidate until all 25 are confirmed.
7. **Stop.** Invalid mode or version, stale or untrusted identity, pause uncertainty, pending or undelivered work, a native rejection, exception, changed provider, conflicting observation, unexpected side effect or timeout ends the run as incomplete or unknown. Do not automatically retry, reset ownership, infer rollback, or resume an unresolved attempt after unload or restart. An already queued or executing native call may not be retractable; the design must prevent unsafe dispatch rather than relying on later cancellation.

The inspected wrapper's `requireMoney=false` branch does not call its `EconomyManager.FetchResource` path. It does not exclude debits by other callbacks or patches, prove the game accepted the tile, or prove a full rollback. Any no-debit claim needs evidence about the actual transaction paths in the selected setup; equal displayed balances are not sufficient.

## Implementation choices

These choices cover the inspected interfaces and call sites, not an exhaustive inventory of every possible area-only API or mod technique.

The authorized `ICities.IAreas` interface exposes start-tile and area-count getters, `maxAreaCount` get/set, `IsAreaUnlocked`, `CanUnlockArea`, `GetAreaPrice` and `UnlockArea`; it exposes no area-milestone-specific setter. This is an inventory of that interface only and does not rule out another game type or extension mechanism.

| Direction | Benefit | Limit or unresolved dependency |
| --- | --- | --- |
| Native `IAreas` calls only | Smallest surface and preserves the native eligibility and extension path. | Can work only when the current maximum and milestone already permit every requested area. In the inspected version the default maximum is nine when its backing field is zero, and a milestone check can reject before `OnCanUnlockArea`; therefore this direction cannot guarantee 25 at startup. |
| Direct `GameAreaManager.UnlockArea(index)` | The inspected concrete method enters synchronously and provides a Boolean after its own native path; it avoids the areas wrapper's additional thread-based queue for that invocation. | It directly depends on game assemblies, still requires a trustworthy manager, city and simulation context, and retains native eligibility and extension callbacks. `true` does not prove funds or persistence; `false` or an exception does not prove complete rollback. A callback can conditionally reenter the same tile before the outer call rechecks ownership, so the Boolean alone is not a safe alternative. |
| Native calls plus an explicitly scoped maximum change and, only if required, a narrowly scoped milestone intervention | May address the identified gates while retaining the native coordinate, ownership and extension checks, with the adapter's own stricter adjacency policy. | `IAreas.maxAreaCount = 25` is itself a game write and may notify milestone listeners. No safe, version-compatible patch mechanism or exact native-invocation identity has been established. A matching caller-supplied token, coordinates or thread alone cannot exclude an unrelated nested call; exceptions, other patches and unwind behavior also need proof. This is research, not a currently executable solution. |

A global milestone override, unlocking all progression milestones, or direct grid mutation would broaden effects beyond the intended area operation and is not recommended. No patch library has been installed or selected. If a safe targeted intervention cannot be established, retain the disabled state and report the feature blocked rather than claim the native API guarantees 25.

For any future implementation, review both build paths: the main project includes `NativeSubmissionCandidate.cs`, while the current hosted workflow's direct source list omits it. Source-list parity, actual release artifacts and live behavior have not been verified by this design.

The direct method would additionally require an authorized reference to `Assembly-CSharp.dll`; its manager's inheritance chain includes `ColossalManaged.dll`. The existing main project and hosted direct compiler list neither reference. The complete isolated compile requirements remain unverified, and no game reference should be bundled with a distributed candidate.

## Minimum path to the 25-area product goal

1. Establish an explicitly supported ordinary-new-city context and a reviewable activation, status and cancellation boundary. The current local candidate has no connected writer or user-operated control; its reference comparisons reduce some risks but do not authenticate the city or make a later call atomic. A single-area experiment is a prerequisite for gathering relevant evidence, not the completed product.
2. Resolve the area maximum for that city. In the inspected reference, a zero backing maximum can initialize to nine during the native eligibility path. Setting `IAreas.maxAreaCount = 25` is a separate game write that can dispatch milestone updates; determine whether it is required and review its effects, timing and compatibility before requesting authorization. Not explicitly setting the maximum does not prove a native call cannot initialize it.
3. Resolve the area milestone gate. `CanUnlock` checks it before `OnCanUnlockArea`, so that callback cannot override an earlier milestone rejection. Investigate an area-only supported route; if a scoped intervention is considered, prove its version, exact call and nesting boundaries, exception cleanup and mod interaction first. No such intervention or dependency is currently implemented or installed.
4. Only after those boundaries are reviewable, implement a default-disabled, per-run coordinator that selects one valid adjacent locked area, calls the selected native path once, checks a newer same-city result, and either continues toward 25 or stops on rejection, ambiguity, exception, unload or conflict. The existing fake-only coordinator cannot authenticate those inputs. The native method's own callbacks can reenter; a local one-shot latch does not prevent another extension from writing.
5. Separately authorize an isolated single-area game test, then a staged 25-area run if the earlier result and risks justify it. Establish actual transaction-path evidence rather than relying on displayed funds alone; examine zone, terrain, achievement, other-mod and save/reload effects under their own approved scopes. Only after appropriate game and distribution evidence should a 25-area release be considered.

The reference supports the `requireMoney=false` wrapper path avoiding its inspected direct fetch and shows a concrete synchronous Boolean alternative; it does not establish the full 25-area goal, absence of every debit, safe milestone intervention, or game compatibility. No 25-area native writer is currently enabled.

### Concrete area-gate strategies

| Strategy | What the inspected reference supports | Remaining boundary |
| --- | --- | --- |
| Set the area maximum and retain all native milestones | The public setter can raise the maximum to 25; if every required area milestone is already passed, native unlocks may proceed. | A fresh city's configured area-milestone values are unknown, so 25 at startup is not guaranteed. A changed maximum can broadcast `MilestonesUpdated`, cause conditional building refresh and achievement effects, and permit larger terrain allocations. The inspected save method does not itself persist the maximum. |
| Temporarily replace only the area-milestone array with a modified clone | For a nonempty `UnlockController.m_AreaMilestones`, clone the array, set only the count's clamped entry on the clone to null, publish the clone with a compare-and-exchange only if the field still holds the original, perform one native attempt, and in `finally` use a second compare-and-exchange to restore the original only if the field still holds that clone. The reference's `Unlocked(int)` treats that null entry as passed; cloning avoids directly changing any aliased original progression-array element or marking the milestone itself passed. The authorized `mscorlib.dll` exposes a generic `Interlocked.CompareExchange<T>` overload, though this complete strategy has not been compiled or executed. | This changes a globally visible area field, not just one call. The area count can change before the native check, so the selected slot may no longer be the one checked. Native milestone checking, guide/UI code and save/deserialization paths can observe the temporary null; reentrant or overlapping scopes can defeat conditional restoration, including ABA. Null or empty arrays require a separate stop path. No stable live configuration, reader exclusion or complete rollback has been established. This is a design candidate, not code to execute. |
| Intervene at the exact native area eligibility call site | A narrowly scoped replacement of only the `Unlocked(count)` result within the intended `GameAreaManager.CanUnlock` invocation could preserve the other native checks and avoid changing milestone arrays or global passed states. | A trustworthy exact call/nesting identity, unwind behavior, version and patch compatibility are not established. No Harmony DLL was found in the authorized reference directory and no dependency was installed; another mechanism or approved existing dependency would have to be reviewed. |

The official global milestone-unlock methods are not an area-only substitute: inspected paths can perform broader checks and conditionally affect rewards, achievements, buildings or roads. Directly editing the area grid and count skips native terrain, zone and extension handling. Neither shortcut is recommended. The clone-and-replace option affects an area-specific field, but it must not be described as affecting only the intended unlock or as proven safe for saves. See [the reference gate inventory](AreaObservationEvidence.md#area-specific-gate-inventory-and-implementation-limits).

For a possible **single-call interception**, the narrow target is the result of `UnlockManager.Unlocked(areaCount)` at `GameAreaManager.CanUnlock` IL_003C–0041, not the global `Unlocked` method or a progression milestone. A future implementation would need to obtain the original result, retain it for all non-target calls and all original successes, override only a failed area gate for the identified current attempt, preserve coordinate, maximum, ownership, adjacency and extension handling, and remove its temporary scope in `finally`. Its one-shot ticket must be consumed or sealed at the first independently identified target evaluation even when the original result is true; the existing synthetic scope leaves it open in that case. Merely using a thread-local flag, matching coordinates or a caller-supplied token is insufficient: an unrelated or nested eligibility call can match or consume that scope, and a nested native unlock can independently affect area counts. An exact relationship to the intended `UnlockArea` invocation and its call site, plus safe exception and reentrancy handling, remains to be established. The inspected `Unlocked(int)` method is non-virtual, so `callvirt` is not a subclass override mechanism.

One concrete design to evaluate is to instrument the `CanUnlock` call at `GameAreaManager.UnlockArea` IL_0011–0014, establish a private scope only for the module's approved synchronous direct call, and track entry and exit depth for the corresponding `CanUnlock`. At the area-gate instruction, retain the actual count argument and original Boolean from the native call rather than rereading the count or calling the original twice. A filter would receive that count, the actual manager, coordinates and original Boolean; a verified outer target consumes its permit once, an original true remains true, and all non-target or uncertain calls retain their original result. If the filter's own decision fails, it must seal the scope and preserve the original result; original exceptions must propagate, and scope cleanup must run even on exceptions. Rewriting the shared `CanUnlock` body would still send all calls through the added filter, so preserving the original Boolean does not prove unchanged timing, exceptions or patch interaction for other callers. This can be evaluated under a controlled version and patch order; it still cannot exclude an earlier reentrant patch impersonating the intended first call without a stronger invocation identity, and it does not prevent a different extension from issuing another native unlock. No such instrumentation has been implemented or verified.

The inspected `IAreasExtension` and `IMilestonesExtension` callbacks do not intercept this early decision. The current module declares no patch dependency, and the authorized reference directory contains no Harmony DLL. No existing usable interception mechanism has been demonstrated under the current no-install constraint; this does not prove that another mechanism is impossible. No patch, array override or native 25-area writer is implemented or activated by this document.

## Smallest useful controlled test

An optional first observation is for the player to inspect an isolated ordinary new city using the existing game screen, without buying or unlocking an area. This needs no new diagnostic UI and can establish only what is visibly displayed in that setup. It cannot authenticate callback origin, simulation thread, forced pause, a coherent internal grid, or transaction behavior. If the existing main module is enabled, its `NewGame` observation path may already read the 25 grid flags twice and the count three times into memory; it is not a lifecycle-only build.

The smallest test of the actual proposed product operation is **one** free native unlock in an isolated ordinary new city, not a full 25-area run. It is currently blocked: the verified city/provider authority, safe execution context and production adapter described above do not exist. After those prerequisites and the exact candidate build are separately reviewed, the proposed test is:

1. Confirm the chosen game and reference version, enabled mods and patches, isolated city, deployment and observation scope. Establish a trustworthy current-city baseline, an initially locked adjacent tile and a count of at most seven, so that a single normal increment does not itself reach the inspected ninth-area achievement condition. The count guard does not rule out other achievement or game effects.
2. Do not call the `maxAreaCount` setter or install a milestone patch for this test. If the maximum or milestone is known to block the attempt, stop. A visible balance comparison is supplementary only, and this single test does not establish absence of all debits, full rollback, 25-area completion, save/reload safety or other-mod compatibility.

Before any future operation, obtain explicit authorization for the exact game and Steam launch context; installation or replacement of a specific candidate DLL and any relevant configuration; the disposable city and any game-owned save, autosave, log, cache or cloud effects; the in-memory grid, count and optional balance observations; the single native area write and its possible zone, terrain, callback or achievement effects; and any evidence retained or shared. ## Harmony 2 call-site assessment — 2026-11-13

**Status: research only.** The following describes a possible future design, not an implemented patch, an enabled writer, a selected Harmony dependency, or evidence of game compatibility. Public references were read on 2026-11-13. No Harmony package was downloaded or installed for this review.

| Mechanism | Official capability | Consequence for the area gate |
| --- | --- | --- |
| Prefix | Runs before the target method and can skip its original body. | A prefix on `CanUnlock` cannot selectively change its internal milestone call while retaining the remaining original checks. Skipping or duplicating that body changes the scope. A prefix on `Unlocked(int)` affects a shared method and needs independently authenticated caller scope. |
| Postfix | Reads or changes the target method's final result. | Changing a final `false` to `true` cannot distinguish milestone rejection from coordinate, maximum, ownership, adjacency or extension rejection. A skipped original and exception handling also matter. |
| Transpiler | Processes a method's IL when a replacement is generated and can identify and alter a particular call instruction. | It is the relevant Harmony 2 mechanism for evaluating the specific call in `CanUnlock`, without changing the shared milestone array. The resulting replacement still applies to the shared method, and every invocation can pass through any inserted filter. |

Sources: [prefix](https://harmony.pardeike.net/v2/articles/patching-prefix.html), [postfix](https://harmony.pardeike.net/v2/articles/patching-postfix.html), [transpiler](https://harmony.pardeike.net/v2/articles/patching-transpiler.html), and [execution flow](https://harmony.pardeike.net/v2/articles/execution.html). In particular, postfix execution is not guaranteed when the original or another patch throws; a finalizer has different exception semantics.

### Candidate matching and failure boundaries

1. Validate the selected loaded method and the expected `UnlockManager.Unlocked(int)` signature against an explicitly supported reference and environment. In the inspected reference, the relevant call is at `CanUnlock` IL_003C, followed by the conditional branch at IL_0041. These offsets are evidence for that reference, not a runtime matching rule. The earlier installed-file hash comparison does not prove which assembly or replacement method is currently executing.
2. Materialize the complete incoming instruction sequence before making changes. Match the exact method operand and suitable surrounding control flow, and require exactly one match. Zero matches, multiple matches, a signature or version mismatch, unsupported instruction structure, or an exception must leave this feature unavailable. Harmony's `CodeMatcher.ThrowIfInvalid` reports an invalid match but does not itself prove uniqueness. Preserve stack types, branch targets, labels and exception blocks; do not assume a fixed instruction offset. See [CodeMatcher](https://harmony.pardeike.net/v2/articles/patching-transpiler-matcher.html) and [CodeInstruction](https://harmony.pardeike.net/v2/articles/patching-transpiler-codes.html).
3. A possible edit retains the original `Unlocked` call and sends its actual Boolean result to an inserted filter before the existing branch. If the filter needs the actual area count, the IL must preserve the already-loaded argument correctly rather than rereading mutable state or calling `Unlocked` a second time. Original successful results and every non-target or uncertain call must retain their original result. A one-shot permit must be sealed at the first independently authenticated target evaluation, even when the original result is already true.
4. Returning the untouched incoming sequence on a mismatch is a candidate for avoiding a partial transformation; that sequence may already include preceding transpilers and is not necessarily vanilla IL. Marking a patch unavailable, matching a sequence, or catching a patch exception is not proof that Harmony atomically restored a previous wrapper or patch registry. The current documentation does not establish safe coordination with in-flight operations or later patch changes. Do not submit an area write unless those boundaries have been established separately.

### Reentry, ordering and runtime

Harmony combines patches and rebuilds replacement methods when patches change. Other prefixes can skip the original, other transpilers can change or remove a match, and later changes can invalidate a previous successful match. Priorities and before/after identifiers help express ordering but do not authenticate the intended call or make unknown modifications compatible. `__state` provides per-invocation prefix/postfix data; it is not an automatic reentrancy guard. `__originalMethod` points to the patched version, so calling it does not bypass the patch. An earlier nested call can still resemble the intended call and consume a thread-local or coordinate-based permit. See [execution flow](https://harmony.pardeike.net/v2/articles/execution.html), [priorities](https://harmony.pardeike.net/v2/articles/priorities.html), and [injected values](https://harmony.pardeike.net/v2/articles/patching-injections.html).

The official [PatchProcessor API](https://harmony.pardeike.net/v2/api/HarmonyLib.PatchProcessor.html) describes `GetCurrentInstructions` after existing transpilers; the inspected [Harmony master MethodCopier source](https://github.com/pardeike/Harmony/blob/master/Harmony/Internal/MethodCopier.cs) reconstructs that sequence using registered transpilers. It must not be treated as an automatically side-effect-free observation or as a permanent snapshot; behavior must be checked against the eventually selected version. Harmony's [unpatching documentation](https://harmony.pardeike.net/v2/articles/basics.html#unpatching) warns that unqualified `UnpatchAll()` removes others' patches. Even an owner-scoped removal rebuilds a shared method and is not demonstrated to cancel an in-flight call or undo its effects. Harmony also documents that [inlining can prevent a patch from running](https://harmony.pardeike.net/v2/articles/patching-edgecases.html).

The official [runtime guidance](https://harmony.pardeike.net/v2/articles/basics.html) requires compatible Harmony code to be available and initialized in the host. The [2.4.3 build configuration](https://github.com/pardeike/Harmony/blob/v2.4.3/Directory.Build.props) includes `net35`, but a build target does not prove compatibility with this specific Unity/Mono host. The [repository](https://github.com/pardeike/Harmony) distinguishes dependency-merged and thin distributions, while its [Unity Mono note](https://github.com/pardeike/Harmony/blob/v2.4.3/Harmony/Internal/HarmonySharedState.cs) warns that only the first of multiple same-named versions may load. No specific Harmony version or distribution has been selected or tested.

Within the reviewed workspace, Full Map declares no Harmony reference. AI_Improve separately declares `CitiesHarmony.API` and has a local API assembly, but that assembly is not the verified `0Harmony` patch implementation and does not establish that Full Map has an available runtime dependency. Its retained restore record is evidence of a past compile-time package resolution, not proof of a deployed or loaded runtime. Reflection or another module's optional loader would not remove the runtime dependency. The current evidence is insufficient to deliver an enabled, independently verifiable 25-area prototype under the no-new-dependency constraint. ### Prefix scope clarification

The Prefix row refers to changing the specific IL call through a method-boundary prefix alone. A prefix can affect the milestone result indirectly by temporarily changing shared milestone state before the original method runs, while allowing its other checks to execute. That changes globally observable state and can be observed by other readers or reentrant calls; it is not a call-site-isolated intervention and has not been implemented or verified here.
