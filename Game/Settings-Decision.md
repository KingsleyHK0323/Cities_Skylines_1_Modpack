# Rate input and storage decision

Signature: OpenAI-Codex

The local candidate prepares a 1x default and a provisional 1.00–10.00 input policy with at most two literal fractional digits. This is an adjustable working default, not a finalized localized UI or a decision about global versus per-city settings. The game entry exposes a provisional settings panel backed only by process memory; its text states that the value is not saved and does not change the game clock. No real persistent store or native clock writer is attached.

## Reference-interface evidence

The approved reference copy looks for a public instance `OnSettingsUI(UIHelperBase)` method by reflection; `IUserMod` itself does not declare that method. `UIHelperBase.AddTextfield` requires a non-null change callback in the inspected implementation. A text-submitted event can also occur on focus loss, so it is not by itself proof that a player explicitly pressed Save. With focus-loss submission disabled, cancellation can restore text without sending the same change event. The candidate explicitly enables focus-loss submission without attaching an apply callback; only its Apply button invokes the temporary setting boundary, using the visible text captured for that click. It limits the field to 128 characters and rejects any 128-character value, so the field's own length truncation cannot turn an overlong entry into an accepted prefix. This does not eliminate transient allocation during a large paste or prove that platform filtering preserves the original input. The optional UI cancel button is disabled until its event ordering is verified.

The candidate checks that its status text is displayed as requested and stops later actions if a status update does not match. That check and the subsequent in-memory submission are not an atomic operation across concurrent UI callbacks. Actual templates, focus ordering, filtering, input methods, callback threading, and visual accessibility have not been tested in the game.

## Storage alternatives

| Candidate | Benefit | Unresolved safety or behavior |
| --- | --- | --- |
| `GameSettings` / `SavedString` | Uses the game's settings infrastructure. | The inspected `InternalAddSettingsFile` load-failure paths can call `SettingsFile.Delete`; a `SavedString` setter can mark data dirty without confirming durable storage. Registering this path would not preserve every corrupted file. |
| Unity `PlayerPrefs` | Provides string keys and a save entry point. | Important operations are native internal calls in the reference copy. Storage scope, preservation of unrelated settings, atomicity, and durable success are not established. |
| A module-owned file | Main's adjustable working direction; it offers a possible isolated scope and format under module control. | The correct game-supported user-data location, global versus per-city scope, cross-process coordination, failure-atomic update, preservation and recovery of corrupt bytes, and target filesystem durability have not been established. An ordinary check followed by overwrite is not an atomic compare-and-exchange. |

The inspected `ColossalFramework.IO.DataLocation.localApplicationData` reference getter is a possible game-provided base for a module-owned file. Its implementation can create the directory when it does not exist, so obtaining the value is not a read-only operation. The reference chooses a platform-dependent base and combines company and product names; the actual location, permissions, installed game version, and platform behavior remain unverified. This getter was inspected, not invoked.

`ISerializableData` is another candidate for simulation-associated data; reference IL shows a dictionary serialized with simulation data, but this does not establish the desired product scope, cross-save isolation in every load path, or durable success. No candidate above is connected to a real store in this batch.

## Reviewable boundary

`ClockRateSettings` and `ClockRateInput` separate valid input, an in-memory draft, explicit submission, and store failures. Draft edits and cancellation do not call `Write`. A store that reports confirmed absence must distinguish it from read failure; a corrupt value is not automatically repaired. A write provider must explicitly report that its operation is finished with no deferred write before the boundary accepts it. An exception or unknown outcome quarantines that settings instance; a single later read is not treated as proof that an old write has stopped. This quarantine belongs only to one settings instance. Another instance or a restarted process may submit a newer value while an earlier unknown write is still pending, after which that earlier write could overwrite the newer one. A real provider must coordinate unresolved operations across instances and restarts, or provide an atomic versioned commit that prevents stale completion; neither guarantee has been implemented or verified. This single-instance string boundary also cannot protect raw container bytes from another writer or prove a durable commit. `Applied` means the provider reported completion and the boundary updated its in-memory value, not that data reached durable storage.

The test-only versioned storage fixture is a model of stronger requirements, not an implementation claim about Unity, Mono, the game, or an operating system. A safe adapter would need a scope-bound version, atomic compare-and-exchange, defensive copies, no ordinary write after corruption or an unknown version, and a way to reconcile ambiguous submissions without guessing from matching content. Migration must be validated without writing and occur only on explicit Save. Conflicting or unavailable evidence must block the write rather than silently overwrite data. In the in-memory fixture, a confirmed not-committed outcome requires a fresh read before an old value can again be treated as confirmed; a started operation with an unknown outcome remains unresolved without a matching receipt. These are fixture behaviors, not guarantees about a real provider.

Before wiring a real provider, establish its storage location and scope, safe lifecycle, concurrent-writer behavior, handling of invalid bytes, operation completion evidence, and failure/termination durability. Do not call `GameSettings.AddSettingsFile` as a shortcut around those gaps.
